## True image-to-video candidate audit

This is a source review, not a browser compatibility claim. The gate is one source image plus a prompt producing newly generated subject motion; camera parallax, optical-flow interpolation, text-only video, and remote inference do not satisfy it. The limit is **2,000,000,000 bytes for the complete downloadable package**, including the model, its required encoders/decoders, engine, license, and metadata. A distilled checkpoint may use fewer inference steps while retaining large weights.

## Catalog tasks and browser paths

The catalog's visual-model details use `src/visualModelSpecs.ts` to show the task, accepted inputs, output types, dimensions, engine, browser backends, format, and pinned weight revision. Pose Landmarker shows its model release and VTracer shows its engine release because those packages do not expose a weight commit hash. The six image generators accept a text prompt and seed and produce PNG images at 512 × 512 pixels, except Supra2-IMG Mobile at 256 × 256. They require WebGPU with `shader-f16`. Depth Anything accepts an image (or a frame generated from a prompt), uses a 518 × 518 depth processor, and can make 512 × 512 parallax frames. RIFE accepts two to six ordered images and interpolates a 256 × 256 or 512 × 512 sequence. Both ONNX motion paths try WebGPU and then WASM. Pose Landmarker processes images or sampled video frames on CPU WASM, VTracer converts raster images to SVG on WASM, and TripoSR accepts a 512 × 512 processed image and outputs a colored mesh using WebGPU with a WASM decoder fallback. These are application paths, not promises that every device supports the model.

## Browser evidence and limits

### Image generation path audit

All six browser image generators currently accept text, optional seed, steps, and prompt strength through `generateImage` and `generateBrowserImage`; they encode the final canvas as PNG. Stable Diffusion 1.5 uses the downloaded Scribbler pipeline, Tiny-SD Q4 and FP16 share the local DPM++ 2M pipeline, SDXS uses its one-step pipeline, DreamShaper 8 LCM uses its LCM pipeline, and Supra2 uses a rectified-flow transformer pipeline. The fixed-step models ignore a general step override. The engine and model files are read from the selected workspace folder.

The downloaded components for each generator contain a text encoder, a denoiser (UNet or transformer), and a **VAE decoder**, but no VAE encoder. The current public generation function has no source-image, mask, latent, denoising-strength, or negative-prompt input. The existing PNG preview is a decode path, not an image-to-image path. Before implementing image-to-image, account for an encoder's download bytes under the package limit and validate the model-specific latent scale, noise, and scheduler behavior.

The [Tiny-SD source repository](https://huggingface.co/cursedhelm/aderpy-deepdreamer-onnx) supplies a VAE encoder in both its Q4F16 and FP16 variant folders. At the [revision already pinned by the app](https://huggingface.co/cursedhelm/aderpy-deepdreamer-onnx/tree/fa62aeaf4ee8a66f77cdc2592983210451857aae), both encoder graphs are the same 68,426,361-byte file with SHA-256 `3cfa0cdc817a9ab0ef545d92c01d2261e2b454b2ebc7ab375cd0ce84ca07fbe1`; both configs specify four latent channels and scale `0.18215`. This is a strong source match for sharing one encoder between Tiny-SD Q4 and FP16, but its graph inputs, browser execution, and output fidelity have not yet been tested. Encoder candidates for the other four image models remain to be evaluated.

The repeatable live checks use **headless Chrome 155 on macOS** with desktop and 390 px mobile viewport emulation. They have generated and inspected output for Supra2-IMG, Depth Anything, RIFE, Pose Landmarker, VTracer, and TripoSR. See the `scripts/check-live-*-output.mjs` checks and the active [visual-dialog checklist](../notes/checklist.md). Mobile viewport emulation does not establish iPhone performance. A physical phone, USB drive, and second machine are still untested.

The size goal in the roadmap says **2 GB**, meaning 2,000,000,000 bytes unless redefined. Stable Diffusion 1.5 already exceeds it with its required engine. RIFE interpolates between supplied frames; it does not predict a new scene. TripoSR returns a static mesh and the live test checked viewer and file integrity, not visual fidelity. Image-generation diagnostics confirm nonempty image output and manual fixture review; they do not establish consistent prompt accuracy.
The catalog labels a visual model **Experimental** when this workspace has no completed saved browser test for it. A failed latest test is shown separately. Custom image prompts do not replace the standard reference-image result; older saved reference tests remain discoverable after a custom run.
New visual diagnostic reports record browser version, platform, device class, viewport, and whether WebGPU and WebAssembly APIs are present. The catalog shows this next to the saved test result. Older reports remain readable and state that browser/device details were not recorded. API availability does not identify which inference backend actually ran.
New successful visual reports now record the selected inference path. Depth Anything and RIFE record whether their ONNX session completed on the requested WebGPU or WASM provider; image generation records WebGPU, Pose Landmarker records CPU/WASM, and VTracer records WASM. TripoSR records its required WebGPU primary session while noting that its decoder permits WASM fallback. ONNX Runtime may still partition individual operators internally, so this field does not measure per-operator execution. Older reports have no backend field.
VTracer was checked with its pinned model and engine files in disposable Chrome: it generated a 128 × 128 SVG and saved a report with `inferenceBackend: "WASM"`. A second generation succeeded with Chrome networking disabled. This verifies VTracer's local path, not every visual model's offline inference path.
Pose Landmarker was also run in disposable Chrome with networking disabled after its pinned files were saved. It processed a synthetic 128 × 128 image, found no person as expected, saved one frame of landmarks, and recorded `inferenceBackend: "CPU/WASM"`. This verifies execution and offline file use; it does not test landmark accuracy on a real person.
Depth Anything and RIFE were each run offline in the same disposable Chrome workspace with their pinned model files and shared ONNX engine. Depth Anything used a synthetic 128 × 128 image to produce a 24-frame camera-motion clip. RIFE used two synthetic images with a shifted circle to produce a three-frame interpolation clip. Both reports passed and recorded `inferenceBackend: "WebGPU"`. These runs verify offline inference and report provenance, not scene or interpolation quality.
The shared motion runtime tries a WebGPU ONNX session, then a WASM session if WebGPU session creation fails. In disposable Chrome, forcing the WebGPU session to throw made RIFE complete interpolation on WASM and report `WASM`; both providers returned the same sampled center pixel for that test. This checks the fallback branch with real inference, not a device that lacks WebGPU. Image generation and TripoSR have no equivalent full CPU path.

## Depth and parallax audit

The depth inspector crops an input image to a 512 × 512 source frame, resizes it to 518 × 518 for Depth Anything, normalizes RGB with ImageNet channel values, and reads the `predicted_depth` tensor. Each output map is scaled from its own finite minimum and maximum into 0–1. A map with no finite values now fails instead of silently producing an all-black result. The renderer samples the map for every source pixel. It reflects pixels beyond image borders instead of stretching one border pixel, but still cannot reconstruct scenery hidden behind a foreground object. The inspector offers depth parallax, horizontal and vertical pan, zoom, and tilt controls in a looping mode. Keyframe mode seeds five poses from the loop and lets users add, remove, reposition, and edit poses with linear, ease-in, ease-out, or smooth interpolation. Clip duration is adjustable from 1–6 seconds and frame rate from 8–24 fps. Frames render on demand to avoid keeping a full clip of 512 × 512 images in memory. The selected mode, poses, duration, and frame rate are saved in the diagnostic report.

The inspector now accepts an optional grayscale PNG depth map in place of estimation. It fits the map to the same 512 × 512 frame, converts RGB luminance and alpha into normalized depth, and saves the map used for each run as a PNG under `media/depth/`. The PNG and WebM have timestamped paths in the report and separate download links. A disposable Chrome test imported a synthetic gradient map, saved a 512 × 512 PNG and a 24-frame WebM, and verified both files in browser storage. This verifies the import and export path; it does not establish the quality of predicted depth on real photographs.
With a synthetic 32 × 32 source file and imported gradient depth map, a separate disposable Chrome run resized the inputs to 512 × 512, changed all five controls, encoded a 24-frame WebM, and saved the selected values in the report (`30px` parallax, `12px` horizontal pan, `-8px` vertical pan, `10%` zoom, `5°` tilt). Separate 32 × 32 pixel checks showed that each control changed the rendered frame. This checks the motion and saved settings path, not scene quality or missing-region repair.
Another disposable Chrome run added a keyframe at 12.5% of the clip, changed its horizontal pan to 18px, and encoded a 24-frame WebM. The saved report recorded six ordered keyframes and the edited pose; easing interpolation returned the expected values at the start, midpoint, and end of sample segments. A 390px viewport showed no horizontal overflow. These checks do not establish visual fidelity on real images.
A further run selected 1 second at 8 fps, saved an eight-frame WebM, and recorded both timing settings in the report. A direct recorder check produced a 1.016-second WebM for that target; MediaRecorder timing is approximate. A border-pixel check confirmed reflected image content fills the area beyond a panned source instead of repeating a flat edge. It does not verify depth-aware repair of occluded scenery.
The depth inspector can explicitly save its loop or keyframe animation, clip duration, and frame rate to `harness/projects/<project-id>/media/depth-camera.json` in the connected workspace. It loads that file when the active project opens; source images remain separate inputs. In a disposable browser workspace, a saved 4-second, 16-fps project preset with six keyframes and an 18px pan restored after changing projects, while another project kept its defaults. The 390px dialog did not overflow horizontally.
The motion inspector can optionally export its frames as a ZIP alongside the WebM. The ZIP contains `sequence.json` with fps, frame count, and dimensions plus numbered PNG files under `frames/`; output frames are generated and written one at a time. A disposable Chrome run saved an eight-frame depth clip and a 75,435-byte ZIP, then unpacked it and decoded the first 512 × 512 PNG. Stopping a ZIP export discards a newly created partial archive.

## RIFE interpolation audit

The pinned RIFE 4.9 package contains a 21,458,882-byte ONNX file and a 1,086-byte MIT license, totaling 21,459,968 bytes. The shared ONNX browser engine adds 26,934,978 bytes, so the complete downloaded package is 48,394,946 bytes. The inspector accepts two to six ordered images, covers each into a selectable 256 × 256 or 512 × 512 frame, and runs one ONNX session across adjacent pairs at evenly spaced timesteps. The 2×, 4×, and 8× settings produce 3, 5, and 9 frames per pair before joining the segments, with incremental still previews. The browser's mobile user-agent path caps input at three images; physical phone performance remains untested.

A model-backed Chrome run in a disposable browser workspace saved a WebGPU RIFE report, a 3,872-byte WebM, and a 49,381-byte ZIP with three numbered 512 × 512 PNGs and a sequence manifest. The red-circle center moved from x=24.5 to 28.6 to 32.5 in 64px samples across those PNGs. A second run verified that the inspector shows first, interpolated, and last-frame stills before encoding finishes, and that the previews fit at desktop and phone widths. This verifies that the exported middle frame differs from the endpoints and lies between them; it does not establish natural-scene quality or artifact rates.
In a fresh disposable Chrome profile, 256 px 4× and 8× runs each saved a WebM and PNG ZIP. The manifests contained the expected 5 and 9 numbered frames at 4 and 8 fps; the report recorded the multiplier and resolution. The browser check verified progressive previews and no horizontal dialog overflow at 1440 px and 390 px. Separate 512 px attempts stalled before the first frame in two profiles, so 256 px is the default while 512 px remains selectable. This does not prove that 512 px is incompatible; a prior single-frame run succeeded.
A three-image 4× run in a fresh Chrome profile saved a nine-frame, 256 px WebM and nine numbered PNGs; the report preserved the ordered intermediate filename. The synthetic red circle moved through all three source positions. The inspector fitted 1440 px and 390 px viewports without horizontal overflow. This verifies the batch path and file output, not natural-scene quality or phone GPU performance.
A later 2× check caught a playback timing fault: MediaRecorder gave the last frame almost no visible hold time, so the WebM appeared to end on the middle frame even though the PNG sequence contained the endpoint. The recorder now holds every frame for one frame interval before flushing. A fresh 2×, 256 px run showed first, middle, and last circle positions at x=24.5, 28.5, and 32.5, and a 1.508-second WebM for three frames at 2 fps. The report identifies the method as `frame-interpolation`. The browser now reads timestamps from the encoded WebM and saves duration, frame intervals, and effective fps. That 2× run recorded 1.507 seconds, four encoded frame blocks including the final flush, and 1.99 effective fps; browser playback reported 1.508 seconds. A deliberately slowed 8 fps recording generated duration, missing-frame, and uneven-timing warnings. Timing analysis is limited to WebM files under 50 MB; a parsing failure is recorded and shown instead of silently assuming the selected fps was achieved.

### Interpolation artifacts to review

RIFE estimates an in-between frame from adjacent source images; it cannot establish unseen scene content. The [RIFE paper](https://arxiv.org/abs/2011.06294) describes motion-boundary correspondence as a difficult part of flow-based interpolation. Review exported PNG frames one by one for doubled or softened edges, bent thin lines or text, and invented detail where a moving object reveals background. These are risks to inspect, **not defects measured in this app's synthetic-circle checks**.

Do not interpolate across a scene cut: unrelated endpoints can yield a blended or warped transition. [Practical-RIFE's author describes a scene-similarity threshold](https://github.com/hzwer/Practical-RIFE/issues/22) for skipping such pairs, while this inspector currently has no cut detector. Keep source images from one continuous shot or split the batch at cuts. The inspector also center-crops inputs to the chosen square size and exports 8-bit PNG and WebM; cropped edges and video compression are separate from model interpolation artifacts. Compare the PNG sequence with the WebM to distinguish inference changes from encoding changes.

Current evidence is limited to synthetic moving circles: the generated positions lay between source positions at 2×, 4×, and 8×. Natural video, thin text, occlusions, scene cuts, and color stability have not yet been scored. Keep the original images, inspect the middle frame and frames next to each source image, and report any visible issue with the input pair, resolution, multiplier, backend, and saved diagnostic JSON.

### FILM comparison

[Google Research FILM](https://github.com/google-research/frame-interpolation) targets interpolation with large motion. Its official release is a TensorFlow 2 SavedModel with [Apache 2.0 source code](https://github.com/google-research/frame-interpolation/blob/main/LICENSE); the [TensorFlow Hub example](https://www.tensorflow.org/hub/tutorials/tf_hub_film_example) accepts two normalized frames plus a time value. A third-party [FP16 safetensors checkpoint](https://huggingface.co/Comfy-Org/frame_interpolation/blob/308e00f486ec04d5b1d63bfd638980c23e7d0b8e/frame_interpolation/film_net_fp16.safetensors) is about 68.9 MB, but that is weights alone, not a browser package or a verified license bundle.

The current app loads ONNX through its optional ONNX browser engine. FILM's official release is not an ONNX asset. [TensorFlow.js describes a Python conversion step](https://github.com/tensorflow/tfjs/blob/master/tfjs-converter/README.md) before loading a SavedModel in the browser; no FILM conversion, browser operator check, package-size audit, or real browser output is verified here. FILM is therefore a research candidate for large-motion quality comparison, not a catalog download or a supported browser model. RIFE remains the tested option at 48,394,946 bytes with its shared engine. A future FILM trial must preserve the app's on-demand third-party download approach and prove conversion/runtime, license, size, offline reuse, and output quality before catalog inclusion.

The catalog also checks the current browser for a WebGPU adapter, `shader-f16`, WebAssembly, and the adapter's maximum buffer and storage binding sizes. It warns when a required browser capability is absent. If the browser exposes `navigator.deviceMemory`, the catalog treats it as a coarse RAM estimate and only cautions when a package download approaches that estimate. Package bytes are disk bytes, not a measured runtime memory requirement; the hardware check cannot guarantee successful inference.
The same details panel detects the directory picker and origin private file storage APIs. Their presence does not grant permission or prove a removable drive is writable; see [privacy and hosting](privacy-and-hosting.md) for the session and USB limits.
