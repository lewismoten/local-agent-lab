# Workspace guide

## Set up a portable folder

1. Open the site while online on each computer you plan to use. The app shell is cached per browser profile; the USB drive carries your workspace files, not the website itself.
2. Insert the drive, choose **Connect drive** in the Workspace panel, and select a folder on that drive. You can select an existing Local Agent Lab workspace or an empty folder. Grant read and write access when your browser asks.
3. Create a small file in **Files & tools**, then confirm it appears on the drive. Project records live under `harness/`; optional model and engine downloads use `models/` and `engines/` in the same folder.
4. Before unplugging, choose **Eject workspace** and wait for the app to finish active file operations and unload models. Then use the computer's drive eject action.
5. On another computer, open the site and connect that same folder. Check the project name and a recent file before continuing. Browser permissions and API keys do not travel with the drive; grant folder access and enter keys again if needed.

Browser file storage is tied to the current browser profile. Choose a drive folder when the work must move between computers. A browser that cannot grant folder access can still use local browser storage, but that storage will stay on that computer.

Browser file saves check the [origin storage estimate](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/estimate) before writing a blob. That estimate is approximate and does not measure free space on a selected USB drive. A drive can still fill or disconnect while writing, so keep a separate copy of important work.

## Workspace

Project settings can make model and agent tools read-only for that project. **Model tools → Workspace model access** can make every project and workspace-scoped agent read-only at once. These rules hide mutating tools from model requests and reject direct write calls, including requests made through agents. A model write checks the current workspace setting again before execution, including a lock set in another tab; you can still edit files yourself in Files & tools.
Open **Model tools** in Files & tools to search the callable tools or filter them by whether they run without asking, need approval, or are blocked. You can allow, block, or require approval for individual tools in the current project. Blocked tools remain listed for review, but are omitted from model requests and rejected if called. Ask-every-time prompts for each call. Ask-once approval can be remembered for the project or only for the current browser session; project approvals can be reset in the tool list.
You can save the current permissions as a named profile and apply it to another project. Project-specific choices override the profile; choosing “Profile” on a tool restores that profile’s setting. Switching profiles clears remembered tool approvals.
Updating a profile sends its new defaults to every linked project while retaining each project's overrides. Removing one keeps each linked project's current effective rules as custom settings.
Open **Conversation tools** beside the chat model controls to use a profile or change individual permissions for that conversation. A project block remains blocked in every conversation. Conversation ask-once approvals stay with that conversation; changing its rules resets those approvals. Updating or removing a shared profile also resets linked conversation approvals, and removal keeps their effective rules as custom choices.

**Project shell** is a simulated, read-only tool for small models that ask for terminal commands. It accepts `pwd`, `ls [-al] [folder]`, `cat file`, and `rg "literal phrase" [folder]` inside the current project's Files area, shown as `/workspace`. `cat` returns a bounded text excerpt; `rg` searches with file and result limits. **Shell commands** has a separate permission for each command, and the parent Project shell permission can block them all. Ask modes use the same approval dialog as other tools. It cannot run scripts, pipes, redirects, or commands that write, delete, or overwrite files.

Tool-capable models initially receive only a context-sized set of tools relevant to the request. When other permitted tools exist, `request_tools` lets the model expose a category (`files`, `edit`, `git`, `library`, `history`, `memory`, `tasks`, `agents`, `journal`, `topics`, `recovery`, `image`, or `shell`) or one named tool for its next step. The offered set is replaced within the same context budget; blocked tools cannot be discovered. This discovery tool can be blocked or set to ask in the tool permissions list.

- **Projects** have their own conversations and file library. **Home** is the default project. Copying or moving a conversation preserves its original messages, search index, compacted chapters, session memory, and chosen icon; the transfer dialog shows progress for long histories and can stop a copy between chunks, removing its incomplete destination while preserving the source. A move checks both source and published destination again before removing the source; if another tab changed either one, the source stays in place. Once a move is confirmed, its old session files and icon reference are removed; if cleanup fails, the destination remains available and the app reports the old files.
- A project can point its code tools at an existing relative folder, such as `repositories/my-app`, inside the connected workspace. Its library and conversation records still live under `harness/projects/<project-id>/`.
- Saved workspace file paths are relative to the selected root. File operations reject absolute, parent-directory, and drive-letter paths. Imported story snapshots must also use relative source and character-image references, so those files can be reopened from another drive location.
- Chat and scheduled agents read `AGENTS.md` from the project's code folder before each run, in addition to Project settings instructions. Without a mapped code folder, place it in the project's Files area. Guides over 16 KB stop the request with an error; shorter guides get their own bounded prompt section so small models still receive some of both instruction sources. The file tools can read the full guide when needed.
- A chat model can read the current Project settings instructions and propose a replacement. Its proposal opens the project editor with the suggested text; it does not save anything until you review and press Save. If the project changed after the proposal, the draft asks for a fresh review. Scheduled agents can read the instructions but cannot propose a replacement.
- **Conversations** are stored in small message chunks. A portable folder combines each completed group of 16 chunks into one verified pack; older conversations can use **Conversation → Optimize files**. Packing stops between groups and preserves readable history if cleanup is interrupted. If a refresh interrupts the metadata save after a chunk was written, opening that conversation recovers its trailing messages. Chat and agent message writes serialize across tabs; a tab with an older conversation view must reopen it before adding a message. Each assistant message records the model and settings used. Compaction keeps a short record of file-changing tool actions; the original events remain with the archived message. Older chunks remain readable after context compaction. The chapter browser groups related compacted parts, searches their titles, summaries, and tags, and opens the original messages without rendering every chapter in chat. When a metadata model is unavailable, a conservative topic check groups related parts and starts a new chapter for unrelated topics. Relevant archived chapters can supply short, source-labeled original excerpts automatically. If chapter metadata omits a detail, recall checks the indexed original messages before giving up; tool-capable profiles can use `list_history_topics`, `search_history`, and `read_history` for more detail. System context is sized to the selected model's input budget.
- New chat answers include **Inspect**, which opens a saved diagnostic with the initial submitted prompt, answer, available thinking text, tool events, model details, usage, timing, and a JSON download. The report is stored separately from message chunks under the conversation's `diagnostics/` folder and copied with the conversation. Seed and temperature show as runtime defaults when the app did not set them. A model's live thinking appears in a collapsible panel when its runtime exposes a stream; providers that hide thinking cannot supply it.
- The chat composer shows estimated context use. Its context control changes the selected model profile, thinking mode, output and context limits, and the workspace's compaction point (60–95% of the estimated input budget). Chat and scheduled agents use the same point. A long exchange can be summarized in multiple bounded parts before its chapter record is saved.
- If a browser response stops or fails after producing visible text, the chat saves that text as an explicitly incomplete assistant message with its model stamp. A stopped request with no visible answer keeps the saved user message without adding an empty assistant reply. File-changing tool runs retain their separate interruption log.
- **Quick open** in the top bar, or ⌘K / Ctrl+K, finds recent conversations by title, tag, preview, or project name across the workspace. Arrow keys and Enter open a result; Discover still provides full-text search and timelines.
- When no browser model is configured, Chat shows the offline starter setup directly. Choose a folder once; the setup continues with the browser engine and model download, then offers Load & test. Other models remain available from the catalog.
- When Chat opens with a saved browser model after a refresh, it loads and briefly checks that model from the connected workspace. A failed check leaves a retry control in Chat and keeps the draft intact. Scheduled agents also prepare their selected browser model before a run; no model weights are downloaded automatically.
- **Discover** ranks tags by how many conversations carry them; clicking one filters by that exact tag. Quick search also checks compacted chapter summaries and opens the matching original chapter. Full-text search uses small per-chunk indexes, including two-character terms in new indexes, to skip unrelated history while verifying matches against the original messages. Older indexes remain searchable and their message chunks are upgraded as short searches inspect them. A hit opens at its matching message; chat history loads automatically as you scroll and keeps a bounded window of rendered messages, with paging buttons and a Latest shortcut available. A shared time scale shows parallel conversations and clickable chapter starts; conversation results and dated topic entries expand in pages.
- **Agents** can run manually, continuously, on an interval, or after a project event while this browser tab is open. Chat and agents share one model queue. Agents have explicit project or workspace file scopes and keep run logs in conversations. Project events queue in the workspace manifest, including while an agent is running or paused; the agent card lists pending events and lets you dismiss an obsolete one after confirmation. A run is claimed before work begins; if the browser closes or the run fails, the agent holds its pending event for review so file-changing tools do not replay automatically. Review the run log, then use **Allow retry** to resume its schedule. An event run uses the project where the event occurred; **Run now** processes a queued event first, otherwise it uses the selected project when in scope. Upcoming runs can be delayed or paused.
- **Tasks** hold workspace or project work items with assignment, status, and dated notes. Assign a task to yourself, leave it unassigned, or choose an agent with access to its scope. Marking a task **Human only** prevents any model from claiming or changing it. An assigned agent sees relevant task IDs in its run prompt and can use `list_tasks`, `read_task`, `claim_task`, `add_task_note`, and `set_task_status`; it must claim the task before adding notes or changing status. An agent must include an explanatory note when marking a task blocked. You can queue an assigned task for an eligible scheduled agent from the Tasks page. Task tools honor project read-only mode and tool permissions. Tasks are saved together in `harness/tasks.json` and serialize across tabs.
- **Identities** are reusable instructions stored with the workspace. Choose a workspace chat default, override it for a project, or assign a preset to an agent. Ada, Lumen, and Trace are editable starting points; New agent picks among the least-used presets and gives repeat agents distinct names, while the template cards let you choose one directly. Existing agents can keep their custom instructions. Each identity has an icon and can use an uploaded or generated avatar. **Surprise me** creates a private draft from a local persona; **Surprise + avatar** also runs your configured image generator. The image prompt is editable, and nothing is saved until you choose **Save identity**. A remote image provider receives the prompt only when you choose to generate.
- **Files & tools** lists and edits project text files. Unsaved editor text is drafted separately for each project and file area in the active workspace, so a refresh or project switch can restore it; opening another file asks before discarding edits. Large folders are shown in 200-entry pages; the model's `list_files` tool returns `nextOffset` for later pages. `search_files` can narrow to a subfolder, scans up to 1,000 text files or 10 MB per call, returns up to three line-and-column matches per file, and gives an offset to continue a limited search. Browser, Ollama, OpenAI-compatible, OpenAI/Codex, Anthropic, and Gemini profiles can request scoped tools to list, search, read bounded portions, edit, move, and delete files in the allowed area. Long tool results are shortened to fit the selected context window; the model can request a smaller range or narrower search. Moves refuse to overwrite an existing file; deletions apply only to files. Exact replacements can be grouped into one checked write. The `apply_patch` tool applies a single-file unified diff with up to 16 context-checked hunks; new files use `write_file`. Stale or ambiguous edits are refused. The editor and `check_syntax` tool can parse JavaScript, TypeScript, JSX, TSX, and JSON files up to 200 KB offline. Model file edits return a brief syntax result automatically. These checks do not typecheck, resolve imports, or run tests. Actual tool use depends on the selected model. Previous versions and removed files are saved under `harness/history/`, and the tool result identifies the backup path. **History** in the Files toolbar lets you download or restore recent labeled backups for the selected project area; restoring over a current file backs that file up first.
- The **Library** file area accepts PDFs and common text, Markdown, data, and code files. Uploads and edits are indexed in the selected workspace. The chat composer can add files with **Add files** or drag and drop, save them to the current project's Library, and insert their paths into the draft. Existing files are kept when an upload has the same name. Use **Update index** after changing library files outside the app. Bulk updates batch manifest writes; Stop flushes finished entries, and the next update can redo an interrupted batch. Its search box shows source-labeled passages, index-scanning and candidate-checking progress, and a Stop control. Chat and agents retrieve short excerpts relevant to the current task; `search_library` can request more and stops when its chat or agent run is cancelled. Search verifies candidate passages against the source text and continues past the first candidate page when needed to find exact phrases. Full documents stay outside the model context. The index skips PDFs over 20 MB and text files over 5 MB, and scans up to 3,000 library files per update.
- Map a project's code folder to an existing repository or initialize Git there. Initialization refuses a folder inside another repository; map the project to that repository's root when it is a project folder. **Files & tools** shows changed and staged files, lets you inspect a bounded diff, stage or unstage individual files, create local commits, and create or switch local branches when the working tree is clean. Branch checkout clears the in-app file editor and refreshes the file list. Scoped `git_init`, `git_status`, `git_history`, and `git_diff` tools let a tool-capable model initialize or inspect its allowed repository; `git_stage`, `git_unstage`, and `git_commit` let it finish a local change when the task calls for it. The `git_create_branch` tool prepares a local branch without switching the user's open files; branch checkout remains in the UI. Commits require an explicit message and author identity; author defaults are saved in the active workspace so they travel with a USB drive. Status pages cover repositories with more than 100 changed files. File edits keep recoverable copies. A model can inspect and restore those copies through scoped tools; replacing a current file requires its freshly inspected SHA-256. Local Git operations work offline. The Git panel also supports remote Clone, Fetch, Pull, and Push when browser network access and the host's CORS policy permit them.
- When an image generator is configured, a tool-capable text model can call `generate_image`. The app runs the image model, saves the image and prompt in the project library, shows the generating model beside the chat preview, reloads a browser text model if needed, and gives the saved path back to the conversation or agent.
- **Model priority** tries tested chat or agent profiles in order. If a server profile fails before running any tool, the next tested profile can answer; a browser fallback remains eligible after another task unloads it and is reloaded from the connected workspace when needed. Once a tool has run, the app stops rather than replaying a possible file edit on another provider. The reply records the model that actually answered and notes any fallback in its tool events.
- Image generators follow the saved priority order. If the current image service is not in that list, it is tried last. An unavailable generator falls through to the next configured option before the text model resumes.
- **Memory** has global, project, and conversation scopes. Relevant entries are retrieved for a request rather than sending the entire library every time. Tool-capable models can use `search_memory` and `read_memory` to inspect additional notes in their allowed project and current conversation. A model can use `propose_memory` to offer a short draft; the chat shows **Review memory**, which opens the editable Memory form. Nothing is saved until you review and submit it. **Remember** on a saved chat message opens the same form with that message as a draft.
- **Journal** is off by default. When enabled, each new chat or agent message adds a short fact to a daily record in the workspace's saved time zone. The Journal page builds readable entries from those facts and available conversation chapter summaries, with links back to the original messages. Links follow a conversation when it is moved to another project. Pausing stops new entries while preserving existing days. `list_journal_days` and `read_journal_day` give permitted models bounded, read-only access to entries in their allowed projects. `get_journal_settings` reads the workspace recording state. In chat, `set_journal_enabled` can turn future recording on or off after showing the current and proposed workspace setting for approval; agents cannot change it. Journal writing is local and uses no model or network request. A journal error does not discard an already saved conversation message; the app reports the separate error.
- `list_project_tags` and `find_tagged_conversations` let permitted models browse the selected project's tag cloud and matching chapter positions using conversation metadata. They do not load full message archives; `search_history` and `read_history` remain available for verifying details in the current conversation.
- `list_agents` shows agents that apply to an allowed project. `propose_agent` creates one bounded, editable draft per response; it cannot save an agent or start a schedule. Open **Review agent** beneath the response to choose the model, access, and schedule before saving.

Portable workspace records are written under `harness/`:

```text
harness/workspace.json
harness/settings.json
harness/avatars/<identity-id>.png
harness/avatars/library.json
harness/images/originals/<image-id>.<format>
harness/git-author.json
harness/memory.json
harness/tasks.json
harness/journal/index.json
harness/journal/days/YYYY-MM-DD.json
harness/projects/<project-id>/project.json
harness/projects/<project-id>/editor-drafts/{files,library}.json
harness/projects/<project-id>/library-index/manifest.json
harness/projects/<project-id>/sessions.json
harness/projects/<project-id>/sessions/<session-id>/chunks/000000.json
harness/projects/<project-id>/sessions/<session-id>/packs/000000.json
harness/projects/<project-id>/sessions/<session-id>/search/000000.json
harness/projects/<project-id>/files/
harness/projects/<project-id>/library/
harness/history/
models/
engines/
sources/
outputs/
presets/
exports/
```

New connected folders start with `models/`, `sources/`, `outputs/`,
`presets/`, and `exports/`. The first project is stored in
`harness/projects/`. Reconnecting an older workspace fills in missing
asset folders when write permission is already granted. A read-only
reconnect opens without asking to create them.

Images made by the chat `generate_image` tool stay in the active
project's `library/generated/` folder. Image inspector runs save
their PNGs under `outputs/images/`. Each PNG has a neighboring
JSON file with its prompt, model, applied seed and settings, and
the pinned hashes of browser model files when available. Remote
providers do not expose a model file hash or an applied seed, so
those fields remain empty rather than implying reproducibility.
When camera-motion video starts from a prompt, its generated first
frame and matching JSON record are saved under `sources/generated/`.
The Images page saves a workspace-wide index of generated and reused
artwork in `harness/avatars/library.json`. Large new images keep their
original file under `harness/images/originals/`; older output files can
be linked into the index without moving or copying them.

Model profiles, the selected profile, and image generator settings travel with the workspace in `harness/settings.json`. API keys stay in browser memory and are cleared when switching workspaces. An existing browser profile setup is imported into the first workspace opened after this update. The model catalog, diagnostics, and engine downloads are inherited from the earlier Story Studio implementation. Its old data format and documentation are preserved in [legacy Story Studio documentation](legacy-story-studio.md); the new app does not silently convert or delete old story files.

Browser Git operations use [isomorphic-git](https://isomorphic-git.org/) and a File System Access adapter. The build generates [third-party notices](../public/licenses/third-party-notices.txt) from installed runtime packages, includes them in the offline app shell, and stops if a new package has no available license text. The **Third-party notices** page lists each package and opens its local license or notice in a readable dialog; the raw text file remains available there. Packages whose npm tarballs omit a license file use local fallback text under `../scripts/license-overrides/`, with its source identified in the generated notice. Optional model and engine licenses are saved separately beside their downloads.

In **Files & tools → Git**, **Clone from remote** uses an empty mapped code folder. Existing repositories can **Fetch**, **Pull**, or **Push** their current branch. Pull requires a clean working tree and only accepts a fast-forward update; push never forces. Each network action opens a dialog showing the repository URL, branch, optional CORS proxy, and optional credentials before it starts. The access token remains in browser memory for that action and is cleared when the dialog closes; the remote URL and proxy can travel in the repository config. A browser needs a Git host that permits cross-origin requests or a proxy you control or trust. No public proxy is preconfigured, and a proxy can see repository traffic and credentials. The local Git HTTP integration test covers all four operations; a published GitHub Pages and removable-drive check is still needed.
